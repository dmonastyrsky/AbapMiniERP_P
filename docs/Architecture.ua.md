## 1. Domain Data Model (Доменна модель даних)

Доменна архітектура складається з 6 бізнес-об'єктів основних даних (Master Data Business Objects) та 4 типів транзакційних документів (Transactional Document types).

### Master Data Entities (Сутності основних даних)
- **Company Code / Балансова одиниця (`ZMERP_COMP_CODE`):** Представляє юридичну особу підприємства, яка відповідає за бізнес-операції. Визначає назву компанії, країну та валюту за замовчуванням.
- **Warehouse / Склад (`ZMERP_WAREHOUSE`):** Представляє фізичне місце зберігання. Кожен склад належить рівно до однієї балансової одиниці (Company Code).
- **Business Partner / Бізнес-партнер (`ZMERP_BUS_PART`):** Представляє зовнішніх контрагентів. Підтримує ролі Клієнта (Customer), Постачальника (Supplier) або комбіновані ролі. Є спільним для всіх балансових одиниць (Company Codes).
- **Item Group / Група матеріалів (`ZMERP_ITEM_GROUP`):** Класифікує матеріали та містить призначення ПДВ за замовчуванням для автоматичного визначення податку.
- **Item Master / Основні дані матеріалу (`ZMERP_ITEM`):** Підтримує фізичні Продукти (Products), які викликають рух запасів, та нематеріальні Послуги (Services) — лише для комерційного розрахунку.
- **VAT Rate / Ставка ПДВ (`ZMERP_VAT_RATE`):** Визначає відсотки податку, на які посилаються групи матеріалів (Item Groups), матеріали (Items) та рядки транзакційних документів.

## 2. Key Generation and Formatting Strategy (Стратегія генерації та форматування ключів)

Система використовує стандартизовані префікси, форматування фіксованої довжини та виділені об'єкти діапазонів номерів (Number Range Objects) для всіх сутностей:

| Entity (Сутність) | Semantic Prefix (Семантичний префікс) | Pattern Example (Приклад шаблону) | Key Generation Strategy (Стратегія генерації ключів) |
|---|---|---|---|
| **Company Code** (Балансова одиниця) | *Немає* | `1000` | Manual Input (Введення вручну) |
| **Warehouse** (Склад) | `WH` | `WH00001` | Early Numbering / Гібридний NRO + DB Max |
| **Business Partner** (Бізнес-партнер) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max |
| **Item Group** (Група матеріалів) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max |
| **Item Master** (Основні дані матеріалу) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max |
| **VAT Rate** (Ставка ПДВ) | `V` | `V0001` | Early Numbering / Гібридний NRO + DB Max |

### Key Generation Logic Flow (Логіка процесу генерації ключів)
1. Користувач створює нову сутність (спрацьовує RAP Early Numbering).
2. Утиліта намагається отримати наступний номер із SAP NRO за допомогою `cl_numberrange_runtime`.
3. Якщо NRO не налаштований або виникає помилка, резервна логіка виконує запит до бази даних для пошуку максимуму `MAX(code)` як в активних таблицях (Active), так і в таблицях чернеток (Draft).
4. Номер інкрементується (збільшується на 1) та форматується з провідними нулями та визначеним семантичним префіксом.

## 3. Master Data Governance & Integrity Patterns (Шаблони управління та цілісності основних даних)

Для забезпечення узгодженості даних, запобігання появі «осиротілих» записів та управління життєвим циклом записів в ABAP Cloud, домен Master Data використовує два стандартизовані шаблони проєктування для всіх бізнес-об'єктів:

### 3.1. Реляційна цілісність через масові попередні перевірки (`precheck_delete`)
Перед видаленням будь-якої сутності Master Data RAP викликає операцію `precheck_delete` у відповідному класі реалізації поведінки (наприклад, `ZBP_MERP_R_COMPANY_CODE`).

Щоб уникнути проблем із продуктивністю під час масового видалення записів, перевірка використовує шаблон масового запиту (Bulk Query Pattern):
- **Дедуплікація ключів:** Цільові ключі з таблиці RAP `keys` збираються та дедуплікуються (`DELETE ADJACENT DUPLICATES`).
- **Масове SQL-сканування залежностей:** Один запит `SELECT DISTINCT` виконується до спеціалізованого ракурсу використання CDS Usage View (наприклад, `ZMERP_I_COMPANY_CODE_USAGE`) з використанням JOIN внутрішньої таблиці (`INNER JOIN @lt_keys`).
- **Зіставлення в пам'яті (In-Memory):** Знайдені залежності зіставляються з окремими записами в пам'яті за допомогою бінарного пошуку (`LOOP AT ... WHERE`).
- **Повідомлення про помилку в RAP:** За наявності залежностей запис позначається як `%fail-cause = if_abap_behv=>cause-dependency`, а зрозуміле повідомлення про помилку (`ZCM_MERP_MESSAGES`) повертається в UI, блокуючи видалення.

### 3.2. М'яке блокування (Soft Blocking) та управління Value Help
Щоб деактивувати сутності Master Data без порушення цілісності історичних транзакційних записів, усі 6 сутностей реалізують поле `IsBlocked` (`ZMERP_IS_BLOCKED`):
- **Збереження даних:** Заблоковані сутності залишаються в базі даних для аудиту та звітності.
- **Запобігання вибору:** Усі спеціалізовані сутності ракурсів підказок вводу Value Help (наприклад, `ZMERP_I_COMPANY_CODE_VH`, `ZMERP_I_VAT_RATE_VH`) застосовують явну умову `WHERE IsBlocked = ''`. Це гарантує, що заблоковані записи Master Data не можна буде вибрати у нових транзакційних документах (PO, SO, рух матеріалів).

## 4. Transactional Document Architecture (Архітектура транзакційних документів — Дизайн Етапу 2)

Транзакційні документи мають композиційну структуру «Заголовок (1) до Позицій (N)» (Header to Line Items):
- **Procurement Chain (Ланцюжок закупівель):** Purchase Order (Замовлення на закупівлю) -> Goods Receipt (Надходження матеріалів)
- **Sales Chain (Ланцюжок продажів):** Sales Order (Замовлення на продаж) -> Goods Issue (Відпуск матеріалів)

### Document Status Lifecycle (Життєвий цикл статусів документів)
- **Open (Відкритий):** Активна чернетка або відкритий документ, доступний для редагування.
- **Posted (Проведений):** Доступний лише для читання (Read-only). Впливає на розрахунок запасів і виступає джерелом для наступних документів.
- **Cancelled (Скасований):** Доступний лише для читання (Read-only). Виключається з розрахунку запасів.

## 5. Dynamic Inventory Calculation Concept (Концепція динамічного розрахунку запасів)

Залишки запасів не зберігаються статично у персистентних таблицях. Поточні рівні запасів розраховуються динамічно в реальному часі на основі проведених документів руху матеріалів:

`Поточний запас = Сума(Проведених надходжень матеріалів) - Сума(Проведених відпусків матеріалів)`

### Rules (Правила):
- Облік ведеться в розрізі Балансової одиниці (Company Code) + Складу (Warehouse) + Матеріалу (Item).
- Виключаються матеріали, де Тип матеріалу (Item Type) = Послуга (`S` / Service).
- Помилки про недостатню кількість запасів на складі примусово застосовуються під час переведення документів відпуску матеріалів (Goods Issue) у статус Проведено (Posted) за допомогою валідацій RAP при збереженні (Validations on Save).
