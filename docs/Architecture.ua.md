## 1. Domain Data Model (Доменна модель даних)[cite: 11]

Доменна архітектура складається з 6 бізнес-об'єктів основних даних та 4 типів транзакційних документів.[cite: 11]

### Master Data Entities (Сутності основних даних)[cite: 11]
- **Company Code / Балансова одиниця (`ZMERP_COMP_CODE`):** Представляє юридичну особу підприємства, яка відповідає за бізнес-операції. Визначає назву компанії, країну та валюту за замовчуванням.[cite: 11]
- **Warehouse / Склад (`ZMERP_WAREHOUSE`):** Представляє фізичне місце зберігання. Кожен склад належить рівно до однієї балансової одиниці.[cite: 11]
- **Business Partner / Бізнес-партнер (`ZMERP_BUS_PART`):** Представляє зовнішніх контрагентів. Підтримує ролі Клієнта, Постачальника або комбіновані ролі. Є спільним для всіх балансових одиниць.[cite: 11]
- **Item Group / Група матеріалів (`ZMERP_ITEM_GROUP`):** Класифікує матеріали та містить призначення ПДВ за замовчуванням для автоматичного визначення податку.[cite: 11]
- **Item Master / Основні дані матеріалу (`ZMERP_ITEM`):** Підтримує фізичні Продукти (рух запасів) та нематеріальні Послуги (лише комерційний розрахунок).[cite: 11]
- **VAT Rate / Ставка ПДВ (`ZMERP_VAT_RATE`):** Визначає відсотки податку, на які посилаються групи матеріалів, матеріали та рядки транзакційних документів.[cite: 11]

## 2. Key Generation and Formatting Strategy (Стратегія генерації та форматування ключів)[cite: 11]

Система використовує стандартизовані префікси, форматування фіксованої довжини та виділені об'єкти діапазонів номерів для всіх сутностей:[cite: 11]

| Entity (Сутність) | Semantic Prefix (Семантичний префікс) | Pattern Example (Приклад шаблону) | Key Generation Strategy (Стратегія генерації ключів) |
|---|---|---|---|
| **Company Code** (Балансова одиниця) | *Немає* | `1000` | Manual Input (Введення вручну)[cite: 11] |
| **Warehouse** (Склад) | `WH` | `WH00001` | Early Numbering / Гібридний NRO + DB Max[cite: 11] |
| **Business Partner** (Бізнес-партнер) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max[cite: 11] |
| **Item Group** (Група матеріалів) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max[cite: 11] |
| **Item Master** (Основні дані матеріалу) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max[cite: 11] |
| **VAT Rate** (Ставка ПДВ) | `V` | `V0001` | Early Numbering / Гібридний NRO + DB Max[cite: 11] |
| **Purchase Order** (Замовлення на закупівлю) | *Префікс компанії* | `1000000001` | Нумерація Early/On-Save / NRO в розрізі компанії |

### Key Generation Logic Flow (Логіка процесу генерації ключів)[cite: 11]
1. Користувач створює нову сутність (спрацьовує RAP Early Numbering).[cite: 11]
2. Утиліта намагається отримати наступний номер із SAP NRO за допомогою `cl_numberrange_runtime`.[cite: 11]
3. Якщо NRO не налаштований або виникає помилка, резервна логіка виконує запит до БД для пошуку максимуму `MAX(code)` в активних таблицях та таблицях чернеток.[cite: 11]
4. Номер інкрементується та форматується з провідними нулями та визначеним семантичним префіксом.[cite: 11]

## 3. Master Data Governance & Integrity Patterns (Шаблони управління та цілісності основних даних)[cite: 11]

Для забезпечення узгодженості даних, запобігання появі «осиротілих» записів та управління життєвим циклом записів в ABAP Cloud, домен Master Data використовує два стандартизовані шаблони проєктування:[cite: 11]

### 3.1. Реляційна цілісність через масові попередні перевірки (`precheck_delete`)[cite: 11]
Перед видаленням будь-якої сутності Master Data RAP викликає операцію `precheck_delete` у відповідному класі реалізації поведінки.[cite: 11]

Щоб уникнути проблем із продуктивністю під час масового видалення записів, перевірка використовує шаблон масового запиту:[cite: 11]
- **Дедуплікація ключів:** Цільові ключі з таблиці RAP `keys` збираються та дедуплікуються (`DELETE ADJACENT DUPLICATES`).[cite: 11]
- **Масове SQL-сканування залежностей:** Один запит `SELECT DISTINCT` виконується до спеціалізованого ракурсу використання CDS Usage View з використанням JOIN внутрішньої таблиці (`INNER JOIN @lt_keys`).[cite: 11]
- **Зіставлення в пам'яті (In-Memory):** Знайдені залежності зіставляються з окремими записами в пам'яті за допомогою бінарного пошуку (`LOOP AT ... WHERE`).[cite: 11]
- **Повідомлення про помилку в RAP:** За наявності залежностей запис позначається як `%fail-cause = if_abap_behv=>cause-dependency`, а зрозуміле повідомлення про помилку повертається в UI.[cite: 11]

### 3.2. М'яке блокування (Soft Blocking) та управління Value Help[cite: 11]
Щоб деактивувати сутності Master Data без порушення цілісності історичних транзакційних записів, усі 6 сутностей реалізують поле `IsBlocked`:[cite: 11]
- **Збереження даних:** Заблоковані сутності залишаються в базі даних для аудиту та звітності.[cite: 11]
- **Запобігання вибору:** Усі спеціалізовані сутності ракурсів підказок вводу застосовують явну умову `WHERE IsBlocked = ''` для запобігання вибору неактивних записів у нових документах.[cite: 11]

## 4. Transactional Document Architecture (Архітектура транзакційних документів — Етап 2)[cite: 8, 11]

Транзакційні документи мають композиційну структуру «Заголовок (1) до Позицій (N)»:[cite: 11]
- **Procurement Chain (Ланцюжок закупівель):** Purchase Order (`ZMERP_R_PURCHASEORDER`) -> Goods Receipt[cite: 8, 11]
- **Sales Chain (Ланцюжок продажів):** Sales Order -> Goods Issue[cite: 11]

### 4.1. Функціональна архітектура замовлення на закупівлю (Purchase Order)

#### Нумерація в розрізі компанії (Company-Scoped Numbering)
- **Контекстно-залежний розподіл NRO:** Номери документів (`DocumentNumber`) генеруються під час збереження за допомогою об'єктів діапазонів номерів, налаштованих для конкретної балансової одиниці (`CompanyCode`), з інтеграцією префікса компанії для унікальної ідентифікації підприємства.[cite: 8]

#### Ядро розрахунку документів (`ZCL_MERP_DOC_CALC`)
- **Розрахунки на рівні позицій:** Зміна кількості (`Quantity`), ціни (`Price`) або коду ПДВ (`VatCode`) ініціює автоматичний перерахунок фінансових сум позиції (`NetAmount`, `VatAmount`, `GrossAmount`) на основі активних ставок податку.[cite: 8]
- **Агрегація загальних сум заголовка:** Зміни фінансових показників позицій миттєво виконують автоматизоване підсумовування загальних сум документа (`TotalNetAmount`, `TotalGrossAmount`) як для активних, так і для чернеток транзакційних екземплярів.[cite: 8]

#### Валідація та обробка повідомлень
- **Очищення помилок UI в реальному часі:** Обробники на основі областей стану очищають специфічні повідомлення валідації полів одразу після їх виправлення.
- **Перевірка на дублікати рядків:** In-memory оцінка контексту запобігає появі однакових `ItemCode` у різних рядках одного документа.[cite: 8]
- **Міжсутності та правила дат:** Забезпечує організаційну узгодженість (узгодження складу з балансовою одиницею, перевірка ролі постачальника) та суворі хронологічні правила дат.[cite: 8]

### 4.2. Document Status Lifecycle (Життєвий цикл статусів документів)[cite: 11]
- **New / Новий (`N`):** Редагована чернетка або нещодавно збережений документ.[cite: 11]
- **Approved / Затверджений (`A`):** Затверджений документ через дію `releaseDocument` (вимагає мінімум 1 позицію).[cite: 11]
- **In Delivery / В доставці (`P`) / Completed / Завершений (`C`):** Стани логістичного виконання.[cite: 11]
- **Cancelled / Скасований (`X`):** Припинений документ через дію `cancelDocument`; виключається з подальших розрахунків.[cite: 11]

## 5. Dynamic Inventory Calculation Concept (Концепція динамічного розрахунку запасів)[cite: 11]

Залишки запасів не зберігаються статично у персистентних таблицях. Поточні рівні запасів розраховуються динамічно в реальному часі на основі проведених документів руху матеріалів:[cite: 11]

`Поточний запас = Сума(Проведених надходжень матеріалів) - Сума(Проведених відпусків матеріалів)`[cite: 11]

### Rules (Правила):[cite: 11]
- Облік ведеться в розрізі Балансової одиниці + Складу + Матеріалу.[cite: 11]
- Виключаються матеріали, де Тип матеріалу = Послуга (`S`).[cite: 11]
- Помилки про недостатню кількість запасів примусово застосовуються під час переведення документів відпуску матеріалів у статус Проведено за допомогою валідацій RAP при збереженні.[cite: 11]
