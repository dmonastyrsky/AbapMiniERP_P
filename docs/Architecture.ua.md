## 1. Domain Data Model (Доменна модель даних)

Доменна архітектура розроблена для підтримки 6 бізнес-об'єктів основних даних та 4 типів транзакційних документів.

### Master Data Entities (Сутності основних даних — Реалізовано)
- **Company Code / Балансова одиниця (`ZMERP_COMP_CODE`):** Представляє юридичну особу підприємства, яка відповідає за бізнес-операції. Визначає назву компанії, країну та валюту за замовчуванням.
- **Warehouse / Склад (`ZMERP_WAREHOUSE`):** Представляє фізичне місце зберігання. Кожен склад належить рівно до однієї балансової одиниці.
- **Business Partner / Бізнес-партнер (`ZMERP_BUS_PART`):** Представляє зовнішніх контрагентів. Підтримує ролі Клієнта, Постачальника або комбіновані ролі. Є спільним для всіх балансових одиниць.
- **Item Group / Група матеріалів (`ZMERP_ITEM_GROUP`):** Класифікує матеріали та містить призначення ПДВ за замовчуванням для автоматичного визначення податку.
- **Item Master / Основні дані матеріалу (`ZMERP_ITEM`):** Підтримує фізичні Продукти (рух запасів) та нематеріальні Послуги (лише комерційний розрахунок).
- **VAT Rate / Ставка ПДВ (`ZMERP_VAT_RATE`):** Визначає відсотки податку, на які посилаються групи матеріалів, матеріали та рядки транзакційних документів.

| **Business Partner** (Бізнес-партнер) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max | Реалізовано |
| **Item Group** (Група матеріалів) | *Немає* | `00001` | Early Numbering / Гібридний NRO + DB Max | Реалізовано |

## 3. Master Data Governance & Integrity Patterns (Шаблони управління та цілісності основних даних)

Для забезпечення узгодженості даних, запобігання появі «осиротілих» записів та управління життєвим циклом записів в ABAP Cloud, домен Master Data використовує два стандартизовані шаблони проєктування:

### 3.1. Реляційна цілісність через масові попередні перевірки (`precheck_delete`)
Перед видаленням будь-якої сутності Master Data RAP викликає операцію `precheck_delete` у відповідному класі реалізації поведінки.

Щоб уникнути проблем із продуктивністю під час масового видалення записів, перевірка використовує шаблон масового запиту:
- **Дедуплікація ключів:** Цільові ключі з таблиці RAP `keys` збираються та дедуплікуються (`DELETE ADJACENT DUPLICATES`).
- **Масове SQL-сканування залежностей:** Один запит `SELECT DISTINCT` виконується до спеціалізованого ракурсу використання CDS Usage View з використанням JOIN внутрішньої таблиці (`INNER JOIN @lt_keys`).
- **Зіставлення в пам'яті (In-Memory):** Знайдені залежності зіставляються з окремими записами в пам'яті за допомогою бінарного пошуку (`LOOP AT ... WHERE`).
- **Повідомлення про помилку в RAP:** За наявності залежностей запис позначається як `%fail-cause = if_abap_behv=>cause-dependency`, а зрозуміле повідомлення про помилку повертається в UI.

### 3.2. М'яке блокування (Soft Blocking) та управління Value Help
Щоб деактивувати сутності Master Data без порушення цілісності історичних транзакційних записів, усі 6 сутностей реалізують поле `IsBlocked`:
- **Збереження даних:** Заблоковані сутності залишаються в базі даних для аудиту та звітності.
- **Запобігання вибору:** Усі спеціалізовані сутності ракурсів підказок вводу застосовують явну умову `WHERE IsBlocked = ''` для запобігання вибору неактивних записів у нових документах.

## 4. Transactional Document Architecture (Архітектура транзакційних документів)

Обсяг транзакційних документів поділяється на ланцюжки закупівель та продажів:

### Procurement (Ланцюжок закупівель)
- **Purchase Order (`ZMERP_R_PURCHASEORDER`) — Реалізовано:** Композиційна структура «Заголовок до Позицій» для обробки процесів створення та затвердження замовлень на закупівлю.
- **Goods Receipt (Надходження матеріалів) — Заплановано:** Майбутній тип документа для фіксації фактичного надходження товарів за замовленнями.

### Sales (Ланцюжок продажів)
- **Sales Order (Замовлення на продаж) — Заплановано:** Майбутній тип документа для управління замовленнями покупців.
- **Goods Issue (Відпуск матеріалів) — Заплановано:** Майбутній тип документа для фіксації відвантаження товарів покупцям.

### 4.1. Функціональна архітектура замовлення на закупівлю (Purchase Order — Реалізовано)

#### Нумерація в розрізі компанії (Company-Scoped Numbering)
- **Контекстно-залежний розподіл NRO:** Номери документів (`DocumentNumber`) генеруються під час збереження за допомогою об'єктів діапазонів номерів, налаштованих для конкретної балансової одиниці (`CompanyCode`), з інтеграцією префікса компанії для унікальної ідентифікації підприємства.

#### Ядро розрахунку документів (`ZCL_MERP_DOC_CALC`)
- **Розрахунки на рівні позицій:** Зміна кількості (`Quantity`), ціни (`Price`) або коду ПДВ (`VatCode`) ініціює автоматичний перерахунок фінансових сум позиції (`NetAmount`, `VatAmount`, `GrossAmount`) на основі активних ставок податку.
- **Агрегація загальних сум заголовка:** Зміни фінансових показників позицій миттєво виконують автоматизоване підсумовування загальних сум документа (`TotalNetAmount`, `TotalGrossAmount`) як для активних, так і для чернеток транзакційних екземплярів.

#### Валідація та обробка повідомлень
- **Очищення помилок UI в реальному часі:** Обробники на основі областей стану очищають специфічні повідомлення валідації полів одразу після їх виправлення.
- **Перевірка на дублікати рядків:** In-memory оцінка контексту запобігає появі однакових `ItemCode` у різних рядках одного документа.
- **Міжсутності та правила дат:** Забезпечує організаційну узгодженість (узгодження складу з балансовою одиницею, перевірка ролі постачальника) та суворі хронологічні правила дат.

### 4.2. Життєвий цикл статусів замовлення на закупівлю
- **New / Новий (`N`):** Редагована чернетка або нещодавно збережений документ.
- **Approved / Затверджений (`A`):** Затверджений документ через дію `releaseDocument` (вимагає мінімум 1 позицію).
- **In Delivery / В доставці (`P`) / Completed / Завершений (`C`):** Стани логістичного виконання (оновлюватимуться в майбутньому документами надходження товарів).
- **Cancelled / Скасований (`X`):** Припинений документ через дію `cancelDocument`; виключається з подальших розрахунків.

## 5. Dynamic Inventory Calculation Concept (Концепція динамічного розрахунку запасів — Цільова модель)

Залишки запасів розраховуватимуться динамічно в реальному часі на основі проведених документів руху матеріалів після повної реалізації транзакційного блоку:

`Поточний запас = Сума(Проведених надходжень матеріалів) - Сума(Проведених відпусків матеріалів)`

*Примітка: Ця концепція запланована до реалізації разом із модулями Надходження матеріалів (Goods Receipt) та Відпуску матеріалів (Goods Issue) на наступних етапах.*
